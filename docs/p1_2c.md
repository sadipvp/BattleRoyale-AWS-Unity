## 2. Software System

**Nombre:** Tank Royale  
**Logo:** `![Tank Royale Logo](https://raw.githubusercontent.com/sadipvp/BattleRoyale-AWS-Unity/main/docs/logo.svg)`

**Descripción:**  
Tank Royale es un videojuego multijugador competitivo de batalla de tanques desarrollado como proyecto del curso de Arquitectura de Software. El sistema sigue una arquitectura distribuida compuesta por: un cliente de juego desarrollado en Unity con Netcode for GameObjects (C#), un backend de microservicios en Python (FastAPI) ejecutado en contenedores Docker, y una infraestructura definida como código mediante AWS CDK (TypeScript).

En el estado actual del prototipo, el sistema funciona completamente en local. Los microservicios backend se ejecutan mediante docker-compose. Para el networking del juego, una instancia de Unity actúa simultáneamente como servidor y cliente (Host) y las demás instancias se conectan como clientes puros.

## 3. Architectural Structures

### 3.1 Estilos Arquitectónicos Utilizados

#### Client-Server

El sistema sigue el estilo **Client-Server** como estilo arquitectónico principal. Los clientes Unity actúan como consumidores de servicios: envían peticiones HTTP al backend para autenticación y matchmaking, y se conectan vía UDP al servidor de juego para gameplay. Los servicios backend (Auth, Matchmaking) actúan como servidores que procesan peticiones y devuelven respuestas.

**Justificación:** En un juego competitivo se necesita una fuente de verdad única para el estado del juego. El servidor autoritario valida toda la lógica crítica (daño, colisiones, spawn), impidiendo que los clientes hagan trampa. En un estilo Peer-to-Peer, cualquier nodo podría alterar el estado, lo que comprometería la integridad competitiva. Además, los servicios de autenticación y matchmaking son inherentemente client-server: hay un servicio central que múltiples clientes consumen.

#### Microservicios

Dentro del estilo Client-Server, el backend se organiza según el patrón arquitectónico de **microservicios**: cada servicio (Auth, Matchmaking) es independiente, con su propia base de datos, su propio Dockerfile, y su propio ciclo de despliegue.

**Justificación:** Permite escalamiento independiente (matchmaking puede tener picos de demanda sin afectar auth), aislamiento de fallos (si matchmaking falla, los usuarios logueados no pierden sesión), y separación de concerns donde cada servicio tiene una responsabilidad única.

### 3.2 Vista de Componente y Conector (C&C)

#### 3.2.1 Descripción General

La vista C&C muestra los elementos con presencia en tiempo de ejecución del sistema Tank Royale y las interacciones entre ellos. Los componentes representan unidades computacionales o almacenes de datos activos durante la operación del sistema. Los conectores representan las vías de interacción en runtime.

En el estado actual del prototipo (ejecución local), no existe un ALB; los clientes Unity realizan peticiones HTTP directamente a los servicios backend por sus puertos locales. El Game Server es una instancia de Unity en modo Host (servidor + cliente en el mismo proceso).

#### 3.2.2 Elementos Arquitectónicos

##### Componentes

| Componente                        | Tipo               | Descripción                                                                                                                                                                                           | Puertos                                                                            |
| --------------------------------- | ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| **Unity Client**                  | Presentación       | Aplicación de juego ejecutada en la máquina del jugador. Gestiona login, lobby, matchmaking y gameplay.                                                                                               | Puerto HTTP (salida hacia servicios backend), Puerto UDP (hacia Game Server)       |
| **Auth Service (FastAPI)**        | Lógica             | Microservicio de identidad. Registra usuarios, valida credenciales, emite y valida JWT. Lenguaje: Python.                                                                                             | Puerto HTTP 8000 (entrada), Puerto SQL 5432 (salida hacia auth-db)                 |
| **Matchmaking Service (FastAPI)** | Lógica             | Microservicio de emparejamiento. Recibe solicitudes de partida, gestiona tickets en DynamoDB. Lenguaje: Python.                                                                                       | Puerto HTTP 8000 (entrada), Puerto DynamoDB (salida), Puerto GameLift API (salida) |
| **Auth Database (PostgreSQL)**    | Datos (Relacional) | Base de datos relacional dedicada. Almacena tabla de usuarios con hash de contraseñas (bcrypt).                                                                                                       | Puerto SQL 5432 (entrada desde Auth Service)                                       |
| **DynamoDB (Tickets + Sessions)** | Datos (NoSQL)      | Tablas NoSQL para tickets de matchmaking efímeros y sesiones de juego activas. TTL automático para auto-limpieza.                                                                                     | API DynamoDB (entrada desde Matchmaking Service)                                   |
| **Game Server (Unity Host)**      | Lógica/Networking  | Servidor autoritario de juego. Actualmente, una instancia de Unity actúa como Host (servidor + cliente en el mismo proceso) ejecutando la simulación física, validando inputs y sincronizando estado. | Puerto UDP 7777 (entrada/salida con clientes)                                      |

##### Conectores

| Conector                                  | Tipo           | Protocolo       | Descripción                                                                                                                                        | Roles                                               |
| ----------------------------------------- | -------------- | --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| **HTTP/REST (Client → Auth)**             | Procedure Call | HTTP/REST       | El cliente envía peticiones HTTP (POST /register, POST /login, GET /me) directamente al Auth Service en puerto 8001. Respuestas en JSON.           | Cliente (requestor) ↔ Auth (responder)              |
| **HTTP/REST (Client → Matchmaking)**      | Procedure Call | HTTP/REST       | El cliente envía peticiones HTTP (POST /join, GET /match-status/{id}) directamente al Matchmaking Service en puerto 8002. Respuestas en JSON.      | Cliente (requestor) ↔ Matchmaking (responder)       |
| **SQL/TCP (Auth → PostgreSQL)**           | Procedure Call | SQL sobre TCP   | Conexión persistente vía asyncpg. Operaciones CRUD sobre la tabla users.                                                                           | Auth Service (caller) ↔ PostgreSQL (executor)       |
| **DynamoDB API (Matchmaking → DynamoDB)** | Procedure Call | HTTPS (API AWS) | Llamadas PutItem, GetItem, UpdateItem sobre tablas MatchmakingTickets y GameSessions vía boto3.                                                    | Matchmaking (caller) ↔ DynamoDB (executor)          |
| **UDP (Client ↔ Game Server)**            | Data Stream    | UDP             | Transporte UDP vía Unity Transport. El cliente envía inputs; el servidor envía snapshots de estado a 30 ticks/segundo. Comunicación bidireccional. | Client (sender/receiver) ↔ Server (sender/receiver) |

#### 3.2.5 Propiedades y Análisis

La vista C&C permite analizar las siguientes propiedades del sistema:

- **Rendimiento:** La separación de canales HTTP (control) y UDP (gameplay) minimiza la latencia en tiempo real. El gameplay no se ve afectado por la latencia de las peticiones REST.
- **Disponibilidad:** Cada componente puede fallar independientemente sin afectar a los demás. Si el Matchmaking Service se cae, los jugadores ya en partida siguen jugando.
- **Seguridad:** El servidor autoritario (Host) valida toda la lógica crítica. Los clientes solo envían inputs y no pueden alterar el estado del juego directamente. La autenticación se maneja mediante JWT stateless.
- **Modificabilidad:** Cada microservicio tiene su propio boundary claro. Se puede cambiar la implementación interna de Auth sin afectar a Matchmaking ni al Game Server.

## 4. Prototype

### 4.1 Requisitos Previos

- Docker Desktop (Docker Engine + Docker Compose)
- Unity 6000.3 LTS con el módulo de Netcode for GameObjects (NGO) 2.10
- Git

### 4.2 Instrucciones para Descargar y Ejecutar

#### Clonar el repositorio

```bash
git clone https://github.com/sadipvp/BattleRoyale-AWS-Unity
cd BattleRoyale-AWS-Unity
```

#### Levantar los servicios backend (docker-compose)

```bash
docker-compose up --build -d
```

Esto levanta los siguientes contenedores:

| Contenedor       | Puerto    | Descripción                                       |
| ---------------- | --------- | ------------------------------------------------- |
| `auth`           | 8001:8000 | Auth Service (FastAPI)                            |
| `matchmaking`    | 8002:8000 | Matchmaking Service (FastAPI, MOCK_GAMELIFT=true) |
| `postgres-auth`  | 5434:5432 | PostgreSQL 15 (base de datos authdb)              |
| `dynamodb-local` | 8000:8000 | DynamoDB Local (modo in-memory)                   |

#### Verificar que los servicios están corriendo

```bash
curl http://localhost:8001/health
# Respuesta esperada: {"status": "ok"}

curl http://localhost:8002/health
# Respuesta esperada: {"status": "ok"}
```

#### Abrir el proyecto en Unity

```bash
# Abrir Unity Hub → Open Project → seleccionar la carpeta Unity_Project/
```

#### Ejecutar el juego (modo local)

1. **Instancia Host (servidor + cliente):**
   - Abrir la escena `Scenes/Login.unity`.
   - Hacer Play en el Unity Editor.
   - Registrar un usuario y hacer login.
   - En la escena Game, presionar **"Host"** para iniciar como servidor + cliente.

2. **Instancias Client (clientes puros):**
   - Abrir una segunda instancia de Unity (ParrelSync o build standalone).
   - Registrar otro usuario y hacer login.
   - En la escena Game, presionar **"Join"** e ingresar la IP del Host (127.0.0.1 para local).

3. **Gameplay:**
   - Movimiento: WASD.
   - El Host ejecuta la lógica autoritativa (validación de colisiones, daño, spawn).
   - Los clientes envían inputs vía UDP y reciben snapshots de estado a 30 ticks/segundo.

#### Detener los servicios

```bash
cd services
docker-compose down
```
